## Summary

Assistente de chat multiagente para planejamento de viagens, exposto via API FastAPI
com frontend web mínimo. Um orquestrador conduz a conversa e delega para subagentes
especializados (voos, hospedagem, roteiro, orçamento) via web search sem API paga.
Um Agente de Milhas totalmente desacoplado responde, independentemente de qualquer
viagem em planejamento, se vale a pena trocar pontos Itaú por milhas com base em
bônus vigentes buscados na web. O sistema é estritamente um assistente de decisão —
nunca executa compras, reforçado tanto no prompt quanto nos testes de aceite.

## What Was Built

### Components

| Component | Description |
|-----------|-------------|
| `core/` | Motor genérico de agente (`loop.py`, `tool_registry.py`, `session.py`, `llm_client.py`, `config.py`) reutilizado por todos os subagentes |
| `orchestrator/` | Agente planejador — conduz a conversa, delega para voos/hospedagem/roteiro/orçamento |
| `agents/voos`, `agents/hospedagem` | Backends de busca via `WebSearchClient` (ddgs, sem API key) |
| `agents/roteiro` | Monta roteiro dia-a-dia via 1 chamada LLM interna |
| `agents/orcamento` | Consolida custo total e sinaliza estouro de orçamento sem bloquear |
| `milhas/` | Agente de Milhas — zero import de `orchestrator/`, calcula valor efetivo por ponto e busca bônus vigente |
| `api/` | FastAPI: `POST /chat/{session_id}`, `POST /miles/query/{session_id}`, `/health`, erros RFC 9457 |
| `frontend/index.html` | Chat mínimo em HTML+JS puro, sem build step |

## Lessons Learned

### Process

- Rodar o build diretamente (build-agent) em vez de delegar para 3 agentes especializados em paralelo (@ai-developer, @api-developer, @python-developer) evitou risco de divergência de contratos compartilhados (`ToolRegistry`, `Session`, `Response`) num codebase greenfield fortemente acoplado por convenção. Para features futuras com múltiplos módulos que compartilham contratos ainda não estabilizados, considerar build direto até os contratos existirem, e só então paralelizar.
- O DESIGN deixou provider de LLM e de busca web como "TBD" — resolver essas decisões explicitamente com o usuário *antes* do build (e não deixar para o build-agent decidir sozinho) evitou retrabalho.

### Technical

- `OpenAI(api_key="")` levanta erro na *construção* do client, não só na chamada — isso quebraria testes/import se o client fosse instanciado eager em `registry.py`. Solução: instanciar o client de forma lazy (dentro do handler, ou via `Depends()` do FastAPI resolvido em request-time), o que também facilita overrides em teste via `app.dependency_overrides`.
- `pytest` insere o diretório do teste em `sys.path` quando não há `tests/__init__.py` — imports de helpers compartilhados devem ser `from conftest import ...`, não `from tests.conftest import ...`.
- Vincular o backend à tool via `functools.partial` no momento do registro (assinatura `(args) -> ToolResult`) simplificou `execute_tool` e evitou passar o backend errado para a tool errada — mais simples que a assinatura `(backend, args)` sugerida no pseudocódigo do DESIGN.

### Communication

- Confirmar o provider de LLM (OpenAI) com o usuário antes do build, mesmo com o DESIGN em aberto, evitou implementar um client genérico demais ou ter que reescrever `llm_client.py` depois.

### Tools & Libraries

- `ddgs` (DuckDuckGo Search) permitiu grounding via web search sem exigir API key nem orçamento — alinhado à constraint de "sem orçamento para APIs pagas" do DEFINE. Trade-off: precisão de preços de voos/hotéis é menor que uma API estruturada (Amadeus/Skyscanner); isolado atrás de `WebSearchClient` para facilitar troca futura.
- `uv` como gerenciador de projeto (via `uv init --package`) funcionou bem para bootstrap rápido do `pyproject.toml`, incluindo config de `ruff` e `pytest` no mesmo arquivo.

## Recommendations for Future Work

| Area | Recommendation |
|------|----------------|
| Precisão de dados | Se a precisão de preços via `ddgs` se mostrar insuficiente em uso real, avaliar migrar `agents/voos` e `agents/hospedagem` para uma API estruturada (Amadeus/Skyscanner), isolada atrás do `WebSearchClient` existente |
| Type checking | mypy não foi configurado neste MVP; considerar adicionar se o codebase crescer além do escopo atual |
| Distill | Avaliar `/distill MULTIAGENTE_VIAGENS` — o padrão de motor genérico (`core/loop.py`) reutilizado por múltiplos subagentes desacoplados (incluindo um agente "satélite" como milhas, com import-check estático de isolamento) parece generalizável para a KB `agentes-llm` |
